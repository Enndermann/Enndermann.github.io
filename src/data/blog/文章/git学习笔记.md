## 引言

我与Git相识已久，大学中我接触了各路大神的代码仓库，现在使用的不少工具都是`Github`上的开源项目。但是我对构建代码仓库的基础技术——Git却是一窍不通。以下是我学习`selierlin`[高质量Git教程](https://selierlin.github.io/git-recipes/#/)的笔记。

## 什么是Git

Git是一个现代化的版本管理系统，由Linux的作者Linus在2005年开发，并逐渐演变为一个成熟的开源项目。

Git有着高性能（分布式架构，通过差分编码保存修改记录）、安全（文件内容和修改信息等都经过SHA1算法加密）和灵活（支持多个非线性工作流、适用于不同规模的项目、兼容多个操作系统和写一）的优势。

## 搭建代码仓库

### `git init`

创建代码仓库，可以将当前目录转为git仓库，或者创建一个空的新仓库。

运行`git init`会在项目根目录下创建一个`.git`目录。

- 直接运行`git init`会将当前目录转为一个Git仓库。

- `git init <directory>`会在当前目录创建一个名为`directory`，只包含`.git`子目录的空目录。
- `git init --bare <directory>`会在当前目录创建一个名为`directory`的裸仓库，忽略工作目录。

> 裸仓库是指仓库中只包含版本修改信息，而不含项目文件。中央仓库、远程仓库通常是裸仓库。

### `git clone <repo> <directory>`

拷贝本地仓库或者克隆远程仓库

### `git config`

在命令行中配置你的Git安装，包括作者姓名、邮箱。

## 保存更改

### `git add <file>/<directory>/-i`

将更改保存到缓存区中。

如果参数为`-i`，开始交互式的缓存。命令行会展示一系列更改，对每项更改，用户输入`y`则加入缓存，输入`n`忽略更改，`s`则将更改分割成更小的块，`e`则手动编辑当前的更改，`q`退出。

### `git commit`

将缓存区中的快照提交到项目历史。

直接运行会弹出文本编辑器，等待用户输入提交信息。

- `git commit -m "<message>"`直接将`message`作为提交信息。

- `git commit -a `跳过缓存区，直接将所有更改提交。

> Git 对提交信息没有特定的格式限制，但约定俗成的格式是：在第一行用 50 个以内的字符总结这个提交，留一空行，然后详细阐述具体的更改。

## 检查仓库状态

### `git status`

查看工作目录和缓存区的状态。主要会列出已缓存、未缓存和未追踪的文件。

#### 忽略文件

未追踪的文件要不是项目新增的、从未提交的文件，要么是编译产生的二进制文件。项目通常不需要保存像后者一样的临时文件，git给出的解决办法是将忽略的目录存在一个`.gitignore`文件中。可以使用通配符+后缀表示一类文件，如`*.pyc`

> 在提交更改前检查仓库状态是一个良好的实践，这样你就不会不小心提交什么奇怪的东西。

### `git log`

显示项目历史信息。

使用默认格式显示完整地项目历史。如果输出超过一屏，你可以用 `空格键` 来滚动，按 `q` 退出。

- `-n <limit>`用 `<limit>` 限制提交的数量。
- `--oneline`将每个提交压缩到一行。当你需要查看项目历史的上层情况时这会很有用。
- `--stat`除了 `git log` 信息之外，包含哪些文件被更改了，以及每个文件相对的增删行数。
- `-p`显示代表每个提交的一堆信息。显示每个提交全部的差异（diff），这也是项目历史中最详细的视图。
- `--author="<pattern>"`搜索特定作者的提交。`<pattern>` 可以是字符串或正则表达式。
- `--grep="<pattern>"`搜索提交信息匹配特定 `<pattern>` 的提交。`<pattern>` 可以是字符串或正则表达式。
- `<since>..<until>`只显示发生在 `<since>` 和 `<until>` 之间的提交。两个参数可以是提交 ID、分支名、`HEAD` 或是任何一种引用。
- `<file>`只显示包含特定文件的提交。查找特定文件的历史这样做会很方便。
- `--graph` 标记会绘制一幅字符组成的图形，左边是提交，右边是提交信息。`--decorate` 标记会加上提交所在的分支名称和标签。`--oneline` 标记将提交信息显示在同一行，一目了然。

> 可以将很多选项放入同一个命令中

## 回滚错误的修改

### `git checkout master/<commit>/<commit> <file>`

将项目/项目中的某个文件回到某次提交/某个分支的状态。

### `git revert <commit>`

生成一个撤销了`<commit>`引入的修改的提交，然后应用到当前分支。

### `git reset`

向前回溯

- `git reset <file>`从缓存区中移除某文件
- `git reset`重设缓存区，匹配上一次提交
- `git reset hard`重设缓存区和工作目录
- `git reset <commit>`将当前分支的末端移到`commit`，将缓存区重设到这个提交。
- `git reset --hard <commit>`将当前分支的末端移到`commit`，并将缓存区和工作目录都设到这个提交。

> 不要重设公共历史

### `git clean -f`

将未被跟踪的文件从工作目录中移除。

`-n`用于查看哪些文件会被移除，`-df`移除未被跟踪的文件和目录，`-xf`移除当前目录下未跟踪的文件，以及 Git 一般忽略的文件。

## 重写项目历史

### `git commit --amend`

将最新提交与缓存中的修改合并，并替换最新提交。

> 不要修复公共提交

### `git rebase <base>`

将当前分支`rebase`到`base`，这里的`base`可以为任何类型的提交引用。

### `git rebase -i <base>`

交互式`rebase`。它会打开一个编辑器，你可以为每个将要 rebase 的提交输入命令，这些命令决定了每个提交将会怎样被转移到新的基上去。你还可以对这些提交进行排序。

### `git reflog`

显示本地仓库的引用日志。

> 引用日志提供的安全网只对提交到本地仓库的更改有效，而且只有移动操作会被记录。

## 保持同步

### `git remote`

添加、查看和删除与其他远程仓库的连接。即维护一份将仓库URL映射到别名的字典。

- 默认命令会列出所有远程连接
- `-v`在会列出所有的远程连接和对应URL
- `add <name> <url>`会创建连接
- `rm <name>`删除连接
- `rename <old-name> <new-name>`重命名

> 当使用`git clone`克隆仓库时，会自动创建一个origin的远程连接指向被克隆仓库。

### `git fetch <remote>`

拉取远程仓库的所有分支，并下载相关提交。再后面加`<branch>`可以拉取指定分支。

拉取下来的分支会另外储存为远程分支。

### `git pull <remote>`

拉取当前分支对应的远程副本，并立即并入本地副本。

加`--remote`后，使用`git rebase`合并远程分支和本地分支。

### `git push <remote> <branch>/--all/--tags`

将本地提交导出到远程分支

> 你只应该推送到那些用 `--bare` 标记初始化的仓库。因为推送会弄乱远程分支结构

## Pull Request

大致的流程如下：

1. 开发者在他们的本地仓库中为某个功能创建一个专门的分支。
2. 开发者将分支推送到公共的 GitHub 仓库。
3. 开发者用 GitHub 发起一个 Pull Request。
4. 其余的团队成员审查代码，讨论并且做出修改。
5. 项目维护者将这个功能并入官方的仓库，然后关闭这个 Pull Request。

## 使用分支

### `git branch`

创建、列出、重命名和删除分支。

- 默认命令会列出仓库中的所有分支
- `<branch>`会创建一个分支
- `-d <branch>`删除指定分支。这是一个安全的操作，Git 会阻止你删除包含未合并更改的分支。
- `-D <branch>`强制删除指定分支，即使包含未合并更改。如果你希望永远删除某条开发线的所有提交，你应该用这个命令。
- `-m <branch>`重命名

Git将分支存为指向提交的引用，分支历史通过提交之间的关系判断。

### `git checkout <existing-branch>`

查看特定分支，分支应该已经通过 `git branch` 创建。这使得 `<existing-branch>` 成为当前的分支，并更新工作目录的版本。

`git checkout -b <new-branch>`创建并查看新分支。加`-`

`git checkout -b <new-branch> <existing-branch>`和上一条相同，但将 `<existing-branch>` 作为新分支的基，而不是当前分支。

> 你应该永远在分支上开发——而绝不在分离的 `HEAD` 上。这样确保你一直可以引用到你的新提交。不过，如果你只是想查看旧的提交，那么是否处于分离 `HEAD` 状态并不重要。

### `git merge <branch>`

将指定分支并入当前分支。

`--no-ff`将指定分支并入当前分支，但 *总是* 生成一个合并提交。

>取决于你的仓库结构，Git 有几种不同的算法来完成合并：快速向前合并或者三路合并。
>
>当当前分支顶端到目标分支路径是线性之时，我们可以采取 **快速向前合并** 。Git 只需要将当前分支顶端（快速向前地）移动到目标分支顶端，即可整合两个分支的历史，而不需要“真正”合并分支。它在效果上合并了历史，因为目标分支上的提交现在在当前分支可以访问到。

## 常见的工作流

### 中心化的工作流

仅有一条分支，所有更改都被提交到这个分支。

### `Feature`分支的工作流

每个功能的开发都可以作为一个单独的分支，开发完成后再通过`pull-request`并入`master`分支。

### `GitFlow`工作流

在`Feature`工作流的基础上，使用两个分支来记录项目历史。`master`分支储存官方发布历史，`develop`分支用来整合功能分支。

加入维护分支，用来快速修复产品bug。维护分支fork自`master`分支，修复完成后应该被并入`master`和`develop`分支。

加入`release`分支，fork自`develop`分支，只有和发布相关的任务应该在这个分支进行，如修复 bug、生成文档等。一旦准备好了发布，发布分支将合并进 `master`，打上版本号的标签。另外，它也应该合并回 `develop`，后者可能在发布启动之后有了新的进展。

### `Fork`工作流

每个开发者fork官方仓库，在服务端创建副本进行开发，完成开发后通过`pull request`并入官方仓库。
